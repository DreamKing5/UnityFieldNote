# 設計・保守メモ

## 採用方式

Supabaseを正本にし、GitHub Pagesは静的配信だけを担当。ユーザーが選択した案Aを採用した。PATを閲覧アプリに扱わせず、本人認証とDB権限を分離できること、ページ分割・索引検索を行えることが理由。

## フロントエンド

Vanilla JavaScriptのES Modules、CSS、ネイティブdialog、ブラウザ標準fetch。実行時のnpmやビルドなし。Supabase REST Auth / Data APIへ接続し、SDKは使用しない。Markdownのみローカル同梱ライブラリ。

通常一覧は24件のタイトル・ジャンル・先頭240文字の概要等だけを取得し、本文はカードを開いたときに取得する。常に24カード以下のDOMとし、「もっと読む」を積み増し続ける方式ではなく前後ページにする。レスポンスはorderとIDのキーページング。本文含む検索はサーバー側で実行し、入力は250ms待って検索する。最新でない検索レスポンスは表示しない。

CSSのぼかしは主にダイアログ背景と＋ボタンに限定。タイムライン全体への高価な背景ぼかし、アニメーション、画像ダウンロードは行わない。

## データモデル

| フィールド | 型 | 意味 |
| --- | --- | --- |
| id | uuid | 一意ID |
| title | text | 1〜180文字 |
| category | text | 1〜60文字、自由入力 |
| body | text | 1〜200,000文字、Markdown |
| tags | text[] | 30個まで、各1〜60文字 |
| created_at | timestamptz | 作成日時 |
| updated_at | timestamptz | 最終更新日時 |
| order | bigint | 日時から独立した表示順 |
| extra | jsonb | 将来の追加フィールド、自由なオブジェクト |
| search_text | text | DB側で生成・更新する検索用の小文字連結テキスト |

新規はmin(order)-1024で先頭へ。インポートは指定の相対順に末尾へ追加する。categoryは別の固定マスターを持たず、記録から抽出する。単独の空ジャンルは保存しない。ジャンル名の変更・統合は一括更新。

## 並べ替え・競合

全記録に対するグローバルなorderを1つだけ持つ。ジャンル内での入れ替えはそのジャンルに属する現在のorder値を再利用するため、他ジャンルの枠は変わらない。全体の整理ではジャンルをまたいで順序変更できる。

整理モードだけは全対象の軽量メタデータを200件ずつ取得し、40件ずつ表示する。取得中にrevisionが変わった場合は中止する。DOMは限定されるが、並べ替え時のメモリ・更新処理は件数に比例する。

各更新はsite_stateの1行をFOR UPDATEでロックし、読み込み時のrevisionを確認する。古ければ拒否する。複数端末でも更新順序を直列化し、silent overwriteを防ぐ。編集、削除、ジャンル名変更、並べ替え、インポートがこの仕組みを共有する。別の記録に対する更新でも競合となる保守的な設計。

JSONエクスポートは全件・全文を取得し、ページ間でrevisionが変わると中止する。並べ替えとインポートは1RPC＝1DBトランザクションで、部分成功しない。

## アクセス制御

公開の読み取りはRLSで許可。APIロールにテーブルへの直接更新権限を渡さない。更新関数だけをauthenticatedロールへ公開し、その関数内でauth.uid()とprivate.ownerの登録UIDを照合する。未認証者は実行権限がなく、別アカウントは関数内のチェックで拒否する。

SECURITY DEFINER関数はRLSを迂回できるため、**全更新で本人確認を最初に実施することが必須**。将来RPCを追加する際もprivate.assert_writerを使う。クライアントのボタン非表示や、公開キーの秘匿には依存しない。

認証トークンはJavaScriptメモリ内のみ。リロード後は閲覧モードに戻る。認証期限が近ければrefresh_tokenで更新する。HTTPS以外の本番接続やsecret/service_roleキーは使わない。

Markdownでは生HTMLを無効化。リンク先プロトコルはmarkdown-itが検査。画像はaltテキスト表示のみ。通常のテキストはtextContentで描画し、外部リンクにはnoopener/noreferrerを指定。CSPで外部scriptとunsafe-evalを許可しない。

## 制約・拡張時の判断

- 誰でも全文を取得・検索・ダウンロードできる公開ノート。アクセス制限が必要なら読み取りRLSも変更する。
- 本番のホスト型Supabase、現行の主要ブラウザを対象。IEや古いWebViewは対象外。
- 全体／ジャンルごとの独立した2種類の順番、画像アップロード、Notion固有ブロック変換、オフライン編集、共同編集、リアルタイムPush通知は未実装。
- 保存時の自動Gitコミットはない。定期的にJSONを書き出す。必要ならSupabase側のバックアッププランも利用する。
- 本文とタグの検索にpg_trgm索引を使用。短い検索語や件数の集計は走査が増える場合がある。
- categories / countは集計クエリ。個人の数千件規模を想定した構成だが、その件数・応答時間を実環境で保証する負荷試験はしていない。
- 数万〜数十万件へ増えた場合は、ジャンル集計キャッシュ、サーバー側の移動先指定RPC、ストリーミングバックアップ等を検討する。
- 24件一覧は本文を送らないが、SQL実行時には検索や概要のために本文を参照する場合がある。
- 新フィールドを追加する場合はまずextraを使用。独立したSQL列にするならmigrationとRPC・入出力の仕様も更新する。
- 認証状態を永続化したい場合は別途設計が必要。単にlocalStorageへトークンを保存する変更を安易に加えない。
